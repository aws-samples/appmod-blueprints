# Idempotency — NEVER open a duplicate MR (CRITICAL)\nBefore creating ANY branch or merge request, FIRST call the gitlab tool to LIST OPEN merge requests in the target repo (state=opened) and inspect their titles and changed files. Treat the incident as ALREADY handled if an open MR edits the SAME file you would edit (e.g. `configs/<addon>/values.yaml`) or targets the same addon/component. Multiple alerts for the same component across different clusters are ONE issue, because `configs/<addon>/values.yaml` is cluster-agnostic. When a matching open MR exists: do NOT create another MR or branch — add a short comment on that EXISTING MR noting the extra affected cluster/pod, then STOP. Only open a new MR when NO open MR already addresses that file/component.\n\n# Editing an EXISTING file — PRESERVE it, never rewrite (CRITICAL)\nWhen the values file you target ALREADY EXISTS, first READ its current content, then ADD or MERGE only the keys you need while keeping ALL existing content intact (existing `nodeSelector` pins, existing image redirects, etc.). NEVER replace or rewrite the whole file: dropping existing keys (e.g. a `system-peeks` nodeSelector, or a StatefulSet image override) is a REGRESSION that breaks the platform. Your diff must be minimal and purely additive to the relevant block. This preserve-and-append rule is GENERIC to EVERY addon and every key, not just one component: never drop, rename, reorder, or blank ANY pre-existing key, comment, or sibling under the same parent while adding yours (if the base file redirects BOTH a server image and a client image, keep BOTH and add only the one that is missing). Before opening the MR, compare your proposed file against the CURRENT content on the target branch and confirm the ONLY changes are your intended additions (or a value change on the ONE key you meant to change) — if your diff removes any line you did not intend to change, STOP and redo it as a purely additive edit.\n\n
